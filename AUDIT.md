## Доказательства и воспроизведение

1. `tests/main_rules`: исходные регрессии с новыми импортами, включая реальный
   Dispatcher в отдельном процессе и подменённые обращения в Telegram.
2. `tests/integration/test_full_workflow.py`: HTTP-авторизация, владение заказами,
   роли, атомарный комментарий, квоты, границы пауз, SQL-бюджет снимка; два
   независимых пула бота/API конкурируют за один слот. Два бариста не могут
   одновременно взять один заказ с одинаковой ревизией.
3. `tests/integration/test_main_import.py`: исходная схема создаётся настоящими
   сохранёнными миграциями main, заполняются все 10 таблиц, затем выполняется перенос.
   Сопоставляются строки и SQLAlchemy metadata, проверяется следующий номер 43
   после импортированного 42. Проверены неизвестная версия, повтор и полный rollback.
4. `frontend/tests/flow.spec.ts`: 13 браузерных сценариев. Включены потерянный ответ,
   очищенный комментарий, 300 emoji, снятие роли, выход из черновика, отсутствие
   двойного пополнения, пустой лимит, окончание паузы и ошибки архива.

Команды:

```powershell
python -m pip install -r requirements-dev.txt
# TEST_DATABASE_URL задаётся отдельно; пароль не добавляется в репозиторий.
python -m pytest -q
cd frontend
pnpm install --frozen-lockfile
pnpm build
pnpm test
```

Без `TEST_DATABASE_URL` проверки PostgreSQL пропускаются; такой запуск не равен
полному результату выше. У роли тестовой БД должно быть право создавать схемы.
В этой проверке все PostgreSQL-тесты выполнены, не пропущены.

## Границы результата

- Реальный аккаунт Telegram, HTTPS-туннель и публикация приложения не запускались.
  Браузерные тесты проверяют React с тестовым API; HMAC initData и серверные права
  проверяются отдельно HTTP-тестами и сравнением с aiogram. Алгоритм сверялся с
  [официальной документацией Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).
- Рабочая база пользователя не переводилась на новую структуру. Для неё нужен
  отдельный явный запуск `python -m app.db.import_main` после остановки прежних
  процессов и создания внешней резервной копии. Внутренняя резервная схема не
  заменяет резервную копию на другом носителе.
- Store всё ещё загружает историю на время операции. Повторные загрузки внутри
  одного ответа устранены, но нагрузочная проверка большого объёма истории и
  адресные SQL-выборки остаются отдельной задачей перед широким запуском.
- Для удаления Telegram-сообщений нужен процесс бота. При работе только API
  очередь сохраняется до его запуска. Оплата по-прежнему не реализована.

Механика переноса таблиц опирается на транзакционный DDL PostgreSQL;
`ALTER TABLE ... SET SCHEMA` переносит также связанные индексы и принадлежащие
таблице последовательности. Это дополнительно проверено реальной миграцией и
rollback, а не только просмотром кода.
[Документация PostgreSQL](https://www.postgresql.org/docs/18/sql-altertable.html).
